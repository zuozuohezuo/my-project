## 1. 首个实现目标

让一个演示县能够连续运行数旬：土地与建筑上的产业实际消耗投入，推进生产并按周期产出；产出按产权进入资源池，三档人口从共用民间池消费；资源短缺产生财富分层的惩罚、死亡和向下转层；结果能够查看、保存和恢复。

第一轮支持县级八组栏目结构，实际运行人口、土地与产权、生产、钱粮、消费及相应人口后果。设施与修正先提供已有条件输入；完整建设升级、市场、税制、迁移生育、官员 AI 和全国经济随后扩展，不将尚未接入的字段显示成已运行机制。

采用独立演示县和演示参数，与 `data/history/` 分开。历史县名、行政索引与人口面积资料仍需分别核对，不通过复制一套示例数值初始化全国。

## 2. 已确认的实现约束

- 三级结构以县为基础；上级汇总不再次生产。同一人口或土地只计一次。
- 人口按贫困、普通、富裕三档消费，基本口粮采用共同人均口径，改善需求按财富层级区别。
- 每县共用民间池，另保留官府与皇家归属。建筑、田地产出进入对应池，消费及生产投入直接扣除，余额不扣成负数。不建立库存预留、占用余额或逐户钱包。
- 短缺时财富越低惩罚越重、死亡率越高，富裕→普通→贫困转层；人口转层保持总量，死亡单独扣除。生存资源和改善资源短缺分别作用。
- 劳力与实物投入有限，农业在收获阶段入库，日常经营持续运行；县经济不逐项消耗皇帝 AP。
- 官府、皇家和民间资源不能因缺口自动混用；国库／内帑、年议定额与财政主官阻止规则继续保留。

## 3. 先准备哪些数据和参数

| 内容 | 首版安排 |
| --- | --- |
| 县身份和人口 | 一县稳定 ID、上级引用、三档人数；年龄、户数、流民与劳力保持一致来源，避免独立总量失配 |
| 土地和建筑 | 面积、用途、质量、产权、当前生产关联；首版建几个明确归属的样例即可 |
| 资源池 | 通用资源余额类型；民间池归 M06，官府／皇家池归 M05，县只引用其 ID |
| 产业样例 | 一种季节性粮食生产、一项需要原料的加工生产；其余行业保留已确认结构 |
| 消费资源 | 先用粮食和少量日用／享受类演示物资检验需求差异；具体商品目录与历史单位另定 |
| 生产参数 | 周期、投入、产出、劳动需求及条件修正，配置标为演示，不写死在页面里 |
| 消费与人口参数 | 人均需求、短缺持续影响、财富惩罚系数、死亡与转层比例及取整方式 |

未定数值先采用独立、可替换的演示配置。它们是原型参数，不据此宣称正式平衡或史实已确认。首版先使用可复现的确定性规则，随机事件以后增加。

群体人数与年龄／劳力统计应从同一人口底账汇总；死亡必须同步影响这些统计。可采用少量财富与年龄交叉群体，不需要逐人或逐户建档。正式年龄段与劳力比例继续配置化。

## 4. 建议的首版结算顺序

在演示规则中明确采用以下顺序，作为实现约定；完整税收、军需和工程介入后的优先级另行讨论。

1. 读取本旬开始的人口、资源、土地条件及生产阶段，确定有限劳力投入。
2. 当前阶段需要的生产投入从对应池直接扣除，不足则缩减或暂停该项生产。
3. 推进生产阶段；到收获或批次完成节点，按建筑／田地产权将实际产出入池。
4. 按各财富群体人数计算消费需求，汇总同资源需求后扣民间池；基本生活优先于使用同种资源的改善需求。
5. 用缺口与持续情况计算三档后果。死亡从各组扣除，降层在存活人数范围内计算并统一转移，本旬新转入下层者不再重复受罚。
6. 汇总期末状态、资源增减、缺口、死亡及转层结果，记录本旬编号；全部校验后提交。

本例允许本旬成熟的产出用于本旬消费。先投生产再消费会影响短缺时的结果，因此该顺序须保存在演示规则版本中，后续调整能明确比较差异，不能让页面操作或字典遍历顺序代替规则。

人口整数化不能导致转出和转入不等；死亡不超过对应人口，转层不超过死亡后的存活人口。对持续低强度变化可保存小数余量或使用明确取整规则，实现时选定一种并验证守恒。居民健康后果与皇帝健康字段分开，不能误扣 `GameState.health`。

旧 v1／v2／v3 档缺少经济数据时继续关闭经济；首个经济演示从 v3 新局入口启用。存在经济数据但结构损坏时明确拒绝读取，不能静默重建为新县。新经济存档不承诺能被旧 EXE 读取。

由于当前旬末函数直接修改状态，接入时需要把同一检查点的计算、校验和应用安排完整；只先扣县粮食再让后续结算失败，会产生半更新。可以先对候选快照计算，无需为一县原型搭建通用事务框架。

## 6. 新脚本与开发顺序

1. **模型与配置**：`core/resources.py`、`core/finance/accounts.py`、`core/regions/models.py`，以及 `data/config/county_demo.json`。定义县状态、池引用、经济参数和旬结果。
2. **独立计算**：`core/regions/production.py`、`consumption.py`、`population.py`、`economy.py`。用 `tools/run_county_demo.py` 连续推进演示县，先检查结果。
3. **会话与存档接入**：统一修改现有 `models.py`、`session.py` 与 `activity_runner.py` 的接点，增加经济编解码及完整校验。
4. **县档案页**：`ui/county_page.py` 展示人口三档、土地建筑、产业阶段、三类归属池、本旬缺口和人口变化。正式游戏只通过现有回合入口推进；独立演示页中的真值须明确是调试／演示视图，M07 信息过滤随后接入。

`core/`、`ui/` 均相对 `src/dynasty/`。这些是拟新增脚本，当前尚不存在。模型和参数约定后，计算与页面可以分别开发，核心会话及存档由同一集成工作处理。

## 7. 验收范围

首版只安排直接证明规则的三组验证：

- **归属与数量一致**：民间、官府、皇家产业各入正确池；消费不负数；人口降层总量守恒、死亡只扣一次；同样短缺下低财富惩罚和死亡率更高。
- **生产周期与旬末时点**：正常生产、持续缺粮、投入不足三种情境可解释；收获只发生一次；场景、急报、劝谏、页面刷新均不额外生产消费。
- **保存恢复与原玩法兼容**：中途存读与连续推进得到同一结果；不同新局资源互不影响；无经济的旧档保持原行为；M03 阶段、转时、诏书及人物目标既有检查继续通过。

人口和池的核心规则先用小型确定性场景验证；接入后运行相关 M03／存档回归，最后检查县页面布局及演示入口。文档更新阶段不运行整套游戏测试，也不引用旧验收数字作为本次结果。

一县通过后，下一步是第二县的实际资源转移与上级汇总，再进入税收、公共支出和 M04 职责设计。
