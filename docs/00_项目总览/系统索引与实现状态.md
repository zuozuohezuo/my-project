# 《大明·御览》系统索引与实现状态

核对日期：2026-09-10。范围：当前源码、配置、测试及已有工作文档。本文是实现状态入口；设计依据仍保留在各专题文件中。返回[工作文件总入口](../README.md)。

## 1. 当前可以怎样玩

当前是 Python + PySide6 的皇帝角色模拟原型。可以安排整旬工作与私生活，按早朝、工作、私生活依次执行，处理中途场景、演示急报和预约；皇帝档案可以编辑和保存。独立县经济试玩会在同一旬末计算生产、消费与人口后果。

普通历史开局没有全国经济模拟。县页展示的是演示县真实数据，尚未经过皇帝情报过滤。史料可浏览，不等于史料中的人物、机构和法令已经参与运行。

本轮没有新增玩法或修改数值。文档分类迁移后，同步调整了游戏内“待确认事项”的读取路径。

## 2. 怎样阅读状态

设计确认与功能实现分开判断，不能互相替代：

| 维度 | 标记 | 含义 |
| --- | --- | --- |
| 设计 | 已确认 | 已有用户决定或现行规则依据；具体适用范围以原文为准 |
| 设计 | 演示默认 | 原型当前采用的参数，可运行，不代表正式平衡或历史统计 |
| 设计 | 待定／候选 | 尚未决定；写进文档不构成确认 |
| 设计 | 历史版本 | 用于追溯；不替代现行规则 |
| 实现 | 演示已运行 | 有运行入口、实际结算或反馈；仅适用于列明的演示范围 |
| 实现 | 部分实现 | 有数据、页面或局部流程，完整系统尚未闭合 |
| 实现 | 未实现 | 当前无对应完整运行逻辑；接口、技能名称、意图记录均不算实现 |

不计算全项目“完成百分比”：正式功能范围和部分规则尚未确定，按文件数或界面数量计算会夸大进展。

## 5. 当前数据归属与结算连接

| 数据／行为 | 当前归属 | 其他模块如何使用 | 必须保持的边界 |
| --- | --- | --- | --- |
| 时钟、阶段、命令提交 | `GameSession` 与 `core/turns/` | 协调人物目标、短期修正与县经济 | 只有完成一旬才结算；点击继续可能只执行一个活动片段 |
| 皇帝整体健康 | `GameState.health` | 决定行动预算并校验现有日程 | 不与县民健康混用；不能另建不同步的健康主值 |
| 皇帝能力、异常、修正、性格、目标 | `GameState.emperor` | 人物页展示，活动实际完成后提交目标进度 | 同一完成事件不能重复计数 |
| 县民、产业、池余额、经济历史 | 可选 `GameState.economy` | M03 旬末调用经济入口；县页读取独立视图 | 民间／官府／皇家余额不自动混用；无经济字段的旧局保持关闭 |
| 县收入 | 人口群体的 `income_per_capita` | 评定财富档 | 是生活水平参数，当前不生成工资，也不凭空增加钱池 |
| 历史资料 | `data/history/`，只读资料适配 | 研究书库、地图与开局快照 | 史料记录不是已任职官员，不自动参与经济 |

实际县经济主顺序是：验证旬序 → 复制候选状态 → 生产 → 消费 → 人口后果 → 汇总报告并校验 → 返回候选结果，由会话提交。生产先处理所有投入再统一入产出，避免靠产业列表先后顺序获得同旬原料链。未来财政模块的数据接管属于设计工作，目前没有完成该拆分。

## 7. 仍需讨论的设计问题

以下是整理后提出的讨论建议，不是已经批准的开发任务：

1. **经济反馈如何变成皇帝决策？** 目前能观察县经济真值，但正式奏报、赈济及财政干预尚未接通，应一起讨论信息和行动入口。
2. **收入何时成为真实收付？** 明确工资、交易、地租和官俸的来源与账户，避免“收入参数”和“钱池”重复计算。
3. **先扩多县还是先补一县治理闭环？** 已有框架提出第二县转移与汇总；具体取舍应结合玩家要验证的决策体验，继续记录在待确认事项。

## 8. 资料优先级与维护

用户最新明确决定优先；其次是现行专题规则和当前代码／测试（分别说明意图与实际行为）。遇到二者不同，记录差异，不擅自把代码当作已批准设计。总览是导航，早期计划和历史验收只说明当时情况。

修改一个规则时，更新对应专题，再同步本索引的状态与证据，以及受影响的参数、试玩说明和验收记录。状态更新须注明核对日期。设计模板和已填写示例见[系统设计模板](../99_模板/系统设计模板.md)及[县级人口系统示例](../01_系统设计/M05_M06_财政与地方经济/M06_人口系统设计_整理示例.md)。
